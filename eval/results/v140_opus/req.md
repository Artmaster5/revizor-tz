**D-083 · 🔴 CRITICAL · Реализуемость.** Изменяющий запрос методом GET

По RFC 9110 метод GET должен быть безопасным, то есть не изменять данные. Метод saveLimit меняет настройку. Прокси, кэши и предзагрузка браузера могут повторить запрос или вернуть сохранённый в кэше ответ. Параметры попадут в журналы.

- Цитаты:
  - строка 104, [REQ-017](#req-017): «REST type \| GET»
  - строка 103, [REQ-016](#req-016): «Description \| Сохранение порога. Функциональные требования: чтение порога»
  - строка 108, [REQ-020](#req-020): «Request URL \| Dev: /alerts/saveLimit . Prod: —»
  - и ещё 4 цитаты: строки 109, 120
- Как исправить: Использовать PUT /alerts/limit (или PUT /cards/\{cardId\}/alert) с телом JSON \{"amount":50000,"enabled":true\}.
- Почему блокер: нарушение стандарта протокола
- Как найдено: правило: «GET для изменяющего запроса (RFC 9110 §9.2.1)» (`get-mutation`); и модель: проверка требования по критерию «реализуемость». Основание: ISO/IEC/IEEE 29148:2018, п. 5.2.5 — требование должно быть реализуемым
- Объединено с похожими замечаниями (6):
  - **Метод GET используется для изменения данных**. Запрос описан как GET, но по пути или описанию он сохраняет или меняет данные («Сохранение», «/alerts/saveLimit», «\$BASE/alerts/saveLimit»). По стандарту HTTP (RFC 9110, п. 9.2.1) GET — безопасный метод, он только читает. Браузеры, прокси… строка 104: «REST type \| GET» (и ещё 3 цитаты).
  - **Сохранение порога выполняется методом GET**. Метод меняет настройку, но вызывается через GET с параметрами в адресе. По стандарту HTTP запрос GET не должен менять данные. Браузеры, прокси и библиотеки могут кэшировать или повторять его без ведома клиента. Сам Description смешивает… строка 103: «Сохранение порога. **D-114 · 🔴 CRITICAL · Непротиворечивость.** Код 200 не гарантирует успех: в теле может быть ERROR

По правилу код 200 означает успех. Но пример для 200 содержит result=ERROR. Клиент, который проверяет только код, примет отказ за успешное сохранение. Кроме того, «и далее» не охватывает коды 3xx и 5xx явно.

- Цитаты:
  - строка 151, [REQ-036](#req-036): «Если результат 200 или 201 — успешный»
  - строка 151, [REQ-036](#req-036): «Если результат 200 или 201 — успешный. Если результат 400, 401 и далее — неуспешный»
  - строка 165, [REQ-043](#req-043): «Successful — Created»
  - и ещё 1 цитата: строка 171
- Как исправить: Записать так: «Ответ с кодом 200 означает успешное сохранение. Любой код 4xx или 5xx означает, что сохранение не выполнено». Код 201 убрать, если метод ресурс не создаёт.
- Почему блокер: нарушение стандарта протокола
- Как найдено: правила: «Коды ответов: упомянутые, но не описанные или перепутанные» (`status-mismatch`); «Ответ с ошибкой под успешным кодом 2xx» (`error-in-success`); и модель: проверка требования по критерию «непротиворечивость». Основание: ISO/IEC/IEEE 29148:2018, п. 5.2.6 — набор требований должен быть непротиворечивым
- Объединено с похожими замечаниями (3):
  - **Код 201 объявлен успешным, но не описан; заголовок 200 подписан «Created»**. Сказано, что успешен ответ 200 или 201, но когда возвращается 201, не описано. Заголовок раздела кода 200 содержит «Created» — это название кода 201. Разработчик может отвечать 201 при первом сохранении, тестировщик будет ждать 200. строка 151: «Если результат 200 или 201 — успешный» (и ещё 1 цитата).
  - **Код ответа 201 назван успешным, но не описан**. В тексте код 201 назван успешным, но в описании ответов для него нет ни условия, ни примера тела ответа. Разработчик не знает, когда его возвращать, а тестировщик — что проверять. строка 151: «Если результат 200 или 201 — успешный».
  - И ещё 1: «Ошибка возвращается с успешным кодом 200»

### 4.2 Взаимная непротиворечивость

<a id="d-032"></a>
**D-032 · 🔴 CRITICAL · Взаимная непротиворечивость.** Лимит «один push в месяц» противоречит push после смены порога

Ф-3 разрешает не больше одного push на карту за календарный месяц. Ф-4 требует push при следующем достижении нового порога «независимо от истории». Пример: push уже ушёл, клиент поднял порог, расходы снова его достигли. По Ф-3 push не отправляется, по Ф-4 отправляется. От выбора зависит, получит ли клиент уведомление.

- Цитаты:
  - строка 39, [REQ-007](#req-007): «На карту приходится максимум один такой push за календарный месяц»
  - строка 40, [REQ-008](#req-008): «следующее достижение вызывает push независимо от истории предыдущей настройки»
  - строка 40, [REQ-008](#req-008): «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки»
- Как исправить: Записать одно правило. Например: «Смена порога сбрасывает признак отправки за текущий месяц; после этого действует ограничение Ф-3 — не более одного push до следующей смены порога или конца месяца».
- Почему блокер: противоречие в документе
- Как найдено: модель, сверка разделов между собой. Основание: ISO/IEC/IEEE 29148:2018, п. 5.2.6 — набор требований должен быть непротиворечивым
- Объединено с похожими замечаниями (4):
  - **Ф-4 разрешает повторный push после смены порога, Ф-3 запрещает второй push в месяце**. Ф-3 ограничивает число push одним на карту за календарный месяц. Ф-4 требует отправить push «независимо от истории», если клиент поднял порог выше накопленной суммы. Возьмём случай: push в этом месяце уже был, клиент поднял порог, и… строка 39: «На карту приходится максимум один такой push за календарный месяц» (и ещё 1 цитата).
  - **Ф-3 «один push в месяц» противоречит Ф-4 «push независимо от истории»**. Ф-3 ограничивает число уведомлений одним в календарный месяц. Ф-4 требует отправить push после смены порога, даже если в этом месяце push уже был. Клиент поднял порог после первого уведомления: один разработчик отправит второй push, другой… строка 39: «На карту приходится максимум один такой push за календарный месяц» (и ещё 1 цитата).
  - И ещё 2: «Ф-3 и Ф-4 расходятся в числе push за месяц после смены порога»; «Неясно, снимает ли смена порога лимит «один push в месяц»»
- Вопрос автору [В-06](#v-06); [подробно](req.details.md#x-d-032)

<a id="d-097"></a>
**D-097 · 🔴 CRITICAL · Взаимная непротиворечивость.** Ошибка проверки суммы возвращается под кодом 200 и одновременно описан код 400

Под заголовком кода 200 приведены два примера ответа: успешный и \{"result":"ERROR"\}. Шаг 5 тоже требует вернуть ERROR при отклонении суммы.   - строка 151, [REQ-036](#req-036): «Если результат 200 или 201 — успешный»
  - строка 162, [REQ-041](#req-041): «Ответ в случае успешного выполнения метода»

- Готовая формулировка — в файле `*.fixed.md` рядом с отчётом.
- Проверка исправления: не проверено кодом — замечание найдено не правилом: код проверил только, что формулировка не теряет значений и смысла; снято ли замечание, без модели не проверить.

**Индекс готовности документа**

**20 из 100 — не готов**. Шкала: 85 и выше — готов, 60–84 — готов после правок, 40–59 — нужна существенная доработка, ниже 40 — не готов.

Как посчитан: 10 × 6,00 (средняя ясность 51 треб.) − 40 (штраф за замечания к набору: 8×4 + 3×13 + 1×30 = 101, но не больше 40) = 20. Ясность — 10 минус вес замечаний, которые называют требование: блокер 6,5, существенное 2,5, мелкое 0,75 (замечание к набору — вдвое меньше); не ниже 1, а без блокера не ниже 4.

Требования по ясности: ясное — 12 · есть замечания — 13 · нужна доработка — 12 · в таком виде использовать нельзя — 14.

Плотность: 1,69 дефекта на одно требование · 85,9 на 1000 слов документа. Вердикт определяют блокеры, а не индекс: индекс показывает, сколько работы осталось.

## Приложение. Как получен отчёт

**Метод.**

1. Документ читается и делится на блоки (абзацы, пункты, строки таблиц); номера строк берутся из исходного текста. Значения, похожие на номера карт и ИИН, маскируются до любой обработки.
2. Блоки делятся на требования и служебные части моделью; программа проверяет, что каждый блок попал ровно в одно место, и сама присваивает номера REQ-….
3. Автоматические правила (набор 1.2: 47 основных и 8 слабых «наблюдений») ищут формальные дефекты: размытые слова, заглушки, единицы измерения, коды и методы HTTP, пустые разделы, схемы без веток ошибок, подсадной текст для ИИ.
4. Модель проверяет каждое требование по семи критериям ISO/IEC/IEEE 29148:2018 п. 5.2.5 тремя отдельными проходами (ясность; полнота и проверяемость; корректность) и весь набор по пяти критериям п. 5.2.6, а проход-критик отвечает на каждый из 35 контрольных вопросов к документу; затем второй, независимый проход перепроверяет каждое замечание.
5. Каждую цитату программа ищет в тексте документа; замечание без найденной цитаты выбрасывается, в отчёт попадает исходный текст, а не пересказ. Номера, индексы, вердикт и отметки в матрице считает программа; перед записью отчёта она проверяет, что его части не противоречат друг другу.

**Честно о границах.** Это первый проход, который экономит время проверяющего; решение остаётся за человеком. Опубликованные замеры ИИ-проверки требований показывают, что лучшие модели находят примерно половину настоящих проблем и ошибочно помечают около одного требования из десяти. Поэтому цитаты сверяет программа, замечания модели перепроверяются вторым проходом, а полнота агента измеряется на контрольных документах, которых он раньше не видел.

**Ограничения этого прогона**

- Рисунки и схемы-картинки не проверяются: учитывается только текст.

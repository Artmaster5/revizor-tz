Комплект из двух документов. Часть B — дочерняя спецификация REST API, на которую ссылается раздел интеграции в части A.

## Часть A. Новый функционал

### Общие сведения

| Поле | Значение |
| :--- | :--- |
| **Наименование задачи** | Регулярное списание с карты в пользу поставщика услуг по расписанию |
| **Продукт** | Мобильный банк для физических лиц |
| **Бизнес-процесс** | Платежи в пользу поставщиков услуг |
| **Business owner / Product owner / Аналитик** | Дирекция розничного бизнеса / владелец продукта «Платежи» / системный аналитик команды платежей |
| **Тип работы** | Новый функционал |
| **Влияние на ИС** | Мобильный банк, сервис автоплатежей, карточный процессинг, шлюз поставщиков услуг, сервис уведомлений |
| **Задача в JIRA** | PAY-2184 |
| **Версия документа** | — |

### Цели
1. Клиент один раз настраивает автоплатёж, после чего связь, интернет и коммунальные услуги оплачиваются без участия клиента.
2. Клиент заранее знает о предстоящем списании: банк уведомляет его за сутки до даты платежа.
3. Снизить число обращений в контакт-центр по поводу забытых оплат коммунальных услуг на 20 % в течение 6 месяцев после запуска.

### Архитектура решения
Мобильное приложение → AutopayService (сервис автоплатежей) → хранилище автоплатежей.
Планировщик → AutopayService → карточный процессинг (списание) → шлюз поставщиков (зачисление) → сервис уведомлений (push).

### Дизайн процесса UI
Платежи → Автоплатежи → «Создать автоплатёж».
На экране создания: выбор поставщика из справочника, поле «Лицевой счёт», поле «Сумма, ₸», выбор периодичности (ежемесячно / еженедельно), выбор дня, выбор карты списания и кнопка «Сохранить».
В списке автоплатежей у каждой записи видны поставщик, сумма, дата следующего списания и статус.
Ошибка проверки поля показывается под этим полем, кнопка «Сохранить» при этом остаётся доступной.

### Требования к изменениям

#### BPMN схема процесса
Наступление даты по расписанию → проверка статуса регулярного платежа → списание с карты → передача платежа поставщику → push клиенту → завершение.
При неуспешном списании процесс переходит к повторной попытке (Ф-5).

#### Функциональные требования
* **Ф-1.** Клиент с активной картой создаёт автоплатёж в пользу поставщика из справочника банка. Сумма фиксированная, от 100 до 500 000 ₸ включительно, целое число тенге.
* **Ф-2.** Списание возможно с любой карты клиента, открытой в банке, в том числе с карты в долларах США или евро.
* **Ф-3.** Периодичность: ежемесячно в выбранный день месяца (от 1 до 31) или еженедельно в выбранный день недели.
* **Ф-4.** Списание выполняется в дату по расписанию в 09:00 по времени Астаны (UTC+5).
* **Ф-5.** Перед каждым списанием клиент подтверждает операцию одноразовым кодом из SMS; без подтверждения списание не выполняется.
* **Ф-6.** Если на карте недостаточно средств, система повторяет попытку списания в течение дня. После трёх неуспешных дней подряд автоплатёж переводится в статус «Ошибка списания».
* **Ф-7.** Клиент может изменить сумму, день и карту списания, поставить подписку на паузу и снять с паузы, а также просмотреть историю списаний за 12 месяцев.
* **Ф-8.** После успешного списания клиент получает push с суммой, названием поставщика и последними четырьмя цифрами карты.
* **Ф-8.** Если шлюз поставщика отклонил платёж из-за неверного лицевого счёта, деньги возвращаются на карту в течение 3 рабочих дней, автоплатёж переводится в статус «Ошибка списания».
* **Ф-9.** Клиент удаляет автоплатёж из списка; удалённый автоплатёж удаляется вместе с историей списаний.
* **Ф-10.** Расписание каждого автоплатежа хранится в Redis в виде cron-строки, планировщик опрашивает Redis раз в минуту.
* **Ф-11.** У клиента не может быть двух активных автоплатежей на один и тот же код поставщика и лицевой счёт.
* **Ф-12.** Если в одну дату с одной карты списывается несколько автоплатежей, они обрабатываются по очереди в порядке возрастания суммы.

### Sequence Diagram
1. Планировщик → AutopayService: наступило время списания, передать список идентификаторов автоплатежей.
2. AutopayService → карточный процессинг: debit (токен карты, сумма).
3. Карточный процессинг → AutopayService: результат списания и RRN.
4. AutopayService → шлюз поставщиков: pay (код поставщика, лицевой счёт, сумма).
5. AutopayService → сервис уведомлений: push клиенту по Ф-8.

### Нефункциональные требования
* Сервис автоплатежей должен работать быстро и надёжно и выдерживать пиковые нагрузки в дни массовых списаний.
* Доступность AutopayService — не ниже 99,9 % за календарный месяц, без учёта согласованных регламентных работ.
* Лицевой счёт и токен карты не выводятся в журналы приложения в открытом виде.

### Требования к данным
Хранить по каждому автоплатежу: идентификатор (UUID), идентификатор клиента, токен карты, код поставщика, лицевой счёт, сумму в тенге, периодичность, день, статус, дату создания.
История списаний (дата и время, сумма, результат, код ответа процессинга, RRN) хранится 5 лет с даты операции по требованию регулятора.

### Требования к интеграции
Приложение создаёт автоплатёж через дочерний документ «Автоплатёж с карты — REST API» (часть B). Методы изменения, паузы и удаления описываются в отдельной спецификации PAY-2185.
Списание выполняется методом debit карточного процессинга. Если процессинг не ответил за 30 секунд, AutopayService повторяет запрос debit до трёх раз.
Если шлюз поставщиков недоступен, платёж ставится в очередь и передаётся повторно каждые 15 минут в течение 24 часов; после этого сумма возвращается на карту.

### Требования к тестированию

#### Тестирование требований
Нагрузочный тест проводится на стенде PREPROD: 50 000 автоплатежей с одной датой списания.

### Критерии приемки

| Исходные условия | Действие | Ожидаемый результат |
| :--- | :--- | :--- |

## Часть B. REST API

Дочерний документ части A: «Автоплатёж с карты — REST API».

### Общие параметры

| Поле | Значение |
| :--- | :--- |
| **Description** | Создание автоплатежа. Функциональные требования: Ф-1, Ф-3, Ф-11 |
| **REST type** | POST |
| **Authorization** | Bearer, сессия клиента мобильного банка |
| **Controller** | AutopayController |
| **URL type** | Dev / Prod |
| **Request URL** | Dev: `/api/v1/autopayments`. Prod: `/api/v1/autopayments` |
| **CURL** | `curl -X POST "$BASE/api/v1/autopayments" -H "Authorization: Bearer $TOKEN" -H "Idempotency-Key: 7f1c2e9a-5b0d-4c8e-9a51-0d3b6f2a1c44" -H "Content-Type: application/json" -d '{"cardId":"tok-8812","providerCode":"ALSECO","account":"4402117","amount":12000,"period":"MONTHLY","dayOfMonth":15}'` |
| **Swagger** | `/swagger/autopay-v1.json` |
| **Gitlab project** | payments/autopay-service |
| **Author** | Системный аналитик команды платежей |
| **Developer** | Команда платежей |

### Логика работы метода
1. Проверить сессию клиента; без действующей сессии вернуть 401.
2. Проверить, что карта `cardId` принадлежит клиенту; иначе вернуть 403.
3. Проверить поля запроса по таблице параметров; при ошибке вернуть 400 с именем первого неверного поля.
4. Если у клиента уже есть активный автоплатёж с тем же `providerCode` и `account`, вернуть 409.
5. Сохранить автоплатёж в статусе ACTIVE, рассчитать дату следующего списания и вернуть 201.

### Особые правила
1. Повторный запрос с тем же заголовком `Idempotency-Key` в течение 24 часов возвращает ответ первого запроса и не создаёт второй автоплатёж.
2. Сумма — целое число тенге, обе границы включены.

### Параметры запроса

#### Headers

| Parameter | Format | Mandatory | Description |
| :--- | :--- | :--- | :--- |
| `Authorization` | string | Да | Bearer-токен сессии |
| `Idempotency-Key` | UUID v4 | Да | Ключ идемпотентности запроса |

#### Request body
* **Content-Type:** `application/json`.

| Parameter | Format | Size | Mandatory | Logic | Description | DB field |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| `cardId` | string | 1–64 | Да | Токен карты клиента | Карта списания | `card_token` |
| `providerCode` | string | 1–20 | Да | Код из справочника поставщиков | Поставщик услуг | `provider_code` |
| `account` | string | 1–30 | Да | Только цифры | Лицевой счёт у поставщика | `account` |
| `amount` | integer | 32 bit | Да | 100–500 000 | Сумма в тенге | `amount_kzt` |
| `period` | string | — | Да | MONTHLY или WEEKLY | Периодичность | `period` |
| `dayOfMonth` | integer | 1–28 | При MONTHLY | 1–28 | День месяца | `day` |
| `dayOfWeek` | integer | 1–7 | При WEEKLY | 1 — понедельник, 7 — воскресенье | День недели | `day` |

### Ответ

| Parameter | Format | Logic | Description |
| :--- | :--- | :--- | :--- |
| `id` | string | UUID | Идентификатор автоплатежа |
| `status` | string | ACTIVE / PAUSED | Статус автоплатежа |
| `nextDebitDate` | string | YYYY-MM-DD | Дата следующего списания |
| `code` | string | При ошибке | Код ошибки |
| `field` | string | При 400 | Имя первого неверного поля запроса |
| `message` | string | При ошибке | Текст ошибки для клиента |

### Статусы

#### 201. Created
```json
{"id":"3d1f7a52-0c8e-4b7a-9f12-6e4a2b9c0d11","status":"ACTIVE","nextDebitDate":"2026-12-15"}
```

#### 400. Bad request
```json
{"code":"VALIDATION_ERROR","field":"amount","message":"Минимальная сумма — 100 ₸"}
```

#### 401. Unauthorized
```json
{"code":"UNAUTHORIZED","message":"Требуется вход"}
```

#### 403. Forbidden
```json
{"code":"CARD_NOT_OWNED","message":"Карта недоступна"}
```

#### 500. Internal server error
```json
{"code":"INTERNAL","message":"Сервис временно недоступен"}
```

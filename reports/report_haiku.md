<a id="d-073"></a>
**D-073 · 🔴 CRITICAL · Полнота.** Не ясно, какая дата определяет месяц покупки

Ф-2 относит покупку к месяцу по дате совершения. Но в примере покупка совершена 31 января, а ожидается рост февральского счётчика при проведении 1 февраля. Разработчик и тестировщик могут по-разному понять, в какой месяц попадает покупка.

- Цитата: строка 64, [REQ-014](#req-014): «Провести 1 февраля в 00:03 по Алматы»
- Как исправить: Указать, какая дата определяет месяц, и привести пример в соответствии с этим правилом.
- Почему блокер: противоречие в документе
- Вопрос автору [В-02](#v-02); [подробно](report_haiku.details.md#x-d-073)

<a id="d-095"></a>
**D-095 · 🔴 CRITICAL · Реализуемость.** Изменение настройки выполняется методом GET

Метод GET по стандарту HTTP предназначен только для чтения. Кэши, прокси и повторные запросы браузера могут выполнить сохранение без ведома клиента. Клиенты, построенные по стандарту, будут работать с сервисом неправильно.

- Цитата: строка 120, [REQ-025](#req-025): «Заменить настройку и вернуть результат сохранения»
- Как исправить: Для операции сохранения использовать метод POST (или PUT, если настройка идентифицируется адресом), а не GET. Изменить строку «REST type» в общих параметрах метода.
- Почему блокер: нарушение стандарта протокола
- Вопрос автору [В-01](#v-01); [подробно](report_haiku.details.md#x-d-095)

### 4.3 Реализуемость, стандарты и безопасность

<a id="d-087"></a>
**D-087 · 🔴 CRITICAL · Реализуемость, стандарты и безопасность.** Сохранение порога описано как GET, хотя метод меняет данные

Метод сохраняет настройку, но в таблице указан тип GET. По HTTP метод GET не должен менять состояние ресурса, а параметры при GET попадают в адрес, журналы и кэш. Пример CURL с флагом -G подтверждает, что данные передаются в строке запроса. Клиент, построенный по стандарту (POST или PUT), не сможет вызвать метод.

- Цитаты:
  - строка 104, [REQ-017](#req-017): «REST type \| GET»
  - строка 103, [REQ-016](#req-016): «Сохранение порога. Функциональные требования: чтение порога»
  - строка 103, [REQ-016](#req-016): «Description \| Сохранение порога. Функциональные требования: чтение порога»
  - и ещё 4 цитаты: строки 108, 109
- Как исправить: Указать REST type: POST (или PUT, если настройка заменяется целиком). Передавать cardId, amount и enabled в теле запроса application/json. Чтение порога описать отдельным методом GET.
- Почему блокер: нарушение стандарта протокола
- Вопрос автору [В-01](#v-01); [подробно](report_haiku.details.md#x-d-087)

## Приложение. Как получен отчёт

**Метод.**

1. Документ читается и делится на блоки (абзацы, пункты, строки таблиц); номера строк берутся из исходного текста. Значения, похожие на номера карт и ИИН, маскируются до любой обработки.
2. Блоки делятся на требования и служебные части моделью; программа проверяет, что каждый блок попал ровно в одно место, и сама присваивает номера REQ-….
3. Автоматические правила (набор 1.1: 27 основных и 8 слабых «наблюдений») ищут формальные дефекты: размытые слова, заглушки, единицы измерения, коды и методы HTTP, пустые разделы, схемы без веток ошибок, подсадной текст для ИИ.
4. Модель проверяет каждое требование по семи критериям ISO/IEC/IEEE 29148:2018 п. 5.2.5 тремя отдельными проходами (ясность; полнота и проверяемость; корректность) и весь набор по пяти критериям п. 5.2.6, а проход-критик отвечает на каждый из 35 контрольных вопросов к документу; затем второй, независимый проход перепроверяет каждое замечание.
5. Каждую цитату программа ищет в тексте документа; замечание без найденной цитаты выбрасывается, в отчёт попадает исходный текст, а не пересказ. Номера, индексы, вердикт и отметки в матрице считает программа; перед записью отчёта она проверяет, что его части не противоречат друг другу.

**Честно о границах.** Это первый проход, который экономит время проверяющего; решение остаётся за человеком. Опубликованные замеры ИИ-проверки требований показывают, что лучшие модели находят примерно половину настоящих проблем и ошибочно помечают около одного требования из десяти. Поэтому цитаты сверяет программа, замечания модели перепроверяются вторым проходом, а полнота агента измеряется на контрольных документах, которых он раньше не видел.

**Ограничения этого прогона**

- Рисунки и схемы-картинки не проверяются: учитывается только текст.
- Агент не знает внутренних стандартов банка и не видит связанных документов, если их не передали через --context.

**Подробности прогона** — в файле `*.diagnostic.md` рядом с отчётом: расход по этапам, отклонённые перепроверкой (4), объединённые повторы (50), выброшенные без подтверждённой цитаты (13). Журнал решений — в JSON-версии (поле `audit`, только хэши текстов): 27 обращений к модели, 151 решение программы.

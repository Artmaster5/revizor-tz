<a id="x-d-029"></a>
**D-029 · 🟡 MAJOR · Реализуемость.** Требование гарантирует доставку push, что технически невыполнимо

- Объединено с похожими замечаниями: «Результат описан через получение клиентом»; «Ф-3 проверяется через получение push клиентом»

<a id="x-v-01"></a>
**В-01.** Какой HTTP-метод использовать для сохранения порога? (кому: архитектор или разработчик; к [D-087](#x-d-087), [D-095](#x-d-095))
- Почему важно: Сейчас сохранение описано как GET. Метод GET не должен менять данные: кэши, прокси и повторные запросы могут сохранить настройку без ведома клиента. Клиенты, построенные по стандарту, не смогут вызвать метод.
- Варианты ответа:
  - а) POST: сохранение и возврат результата в одном методе — что изменится: Метод сохранения станет POST, параметры перейдут из адреса в тело запроса.
  - б) PUT: полная замена настройки по cardId — что изменится: Метод сохранения станет PUT, идемпотентная замена настройки по идентификатору карты.
  - в) Отдельный GET для чтения и POST для сохранения — что изменится: Появится два метода: GET читает порог, POST сохраняет его; оба описываются отдельно.
- Что изменит ответ в итоге: закроет 2 из 7 блокеров · индекс готовности 19 → 22

**В-02.** По какой дате относить покупку к месяцу: по дате совершения или по дате проведения? (кому: аналитик — автор документа; к [D-026](#x-d-026), [D-073](#x-d-073))
- Почему важно: Сейчас Ф-2 говорит «по дате совершения», а пример на границу месяца ждёт рост февральского счётчика при проведении 1 февраля. Итоги по месяцам и срабатывание порога у разных исполнителей разойдутся.
- Варианты ответа:
  - а) По дате совершения покупки (пример исправить: покупка 31 января попадает в январь) — что изменится: В документе останется «по дате совершения», а пример будет переписан на январский месяц.
  - б) По дате проведения покупки (исправить Ф-2 и остальные места, где указана дата совершения) — что изменится: В документе «по дате совершения» будет заменено на «по дате проведения», пример останется как есть.

**В-04.** Какой HTTP-код и тело получает ответ, когда сумма или переключатель введены неверно? (кому: архитектор или разработчик; к [D-100](#x-d-100), [D-124](#x-d-124))

- Варианты ответа:
  - а) HTTP 400 с полем result: ERROR и message — что изменится: Ошибка ввода будет возвращаться кодом 400; пример ответа и раздел статусов приведутся к нему.
  - б) HTTP 422 с полем result: ERROR и message — что изменится: Ошибка ввода будет возвращаться кодом 422; в раздел статусов добавится новый код.
  - в) HTTP 200 с result: ERROR и message (как описано сейчас) — что изменится: Оставить 200 и явно описать признак ошибки в контракте; раздел статусов поправить под это.

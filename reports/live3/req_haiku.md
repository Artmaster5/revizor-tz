**D-001 · 🟢 MINOR · Однозначность.** Термин «личный бюджет» не совпадает с «порогом»

В цели используется «личный бюджет», а в требованиях — «порог». Читатель может решить, что это разные сущности. Для цели это не меняет реализацию, но мешает сверке документа.

- Цитата (строка 23): «личного бюджета в момент покупки»
- Как исправить: Заменить «личного бюджета» на «порога расходов по карте», чтобы термин совпадал с требованиями.

  - б) Да: после смены порога push отправляется, даже если в этом месяце он уже был — что изменится: Ф-3 будет дополнен исключением: после смены порога допускается второй push в месяц.

- Кому: архитектор или разработчик · Тип пробела: не описан сценарий
- Почему важно: Есть только переключатель для одного держателя карты. Без выключателя на уровне системы откат затронет настройки всех клиентов.
- Где в документе: строка 76: «Реализация задачи/проекта предусматривает схему отката решений»
- Варианты ответа:
  - а) Выключатель функции на уровне системы — что изменится: В документ будет добавлено требование к глобальному выключателю и его управлению.
  - б) push не отправляется, данные продолжают сохраняться — что изменится: В документ будет записано поведение отключения отправки push при сохранённых данных.
  - в) Откат релиза без выключателя — что изменится: В документ будет записана процедура отката релиза.
  - г) Скрытие экрана в мобильном приложении без отключения сервиса push — что изменится: В документ будет записано скрытие экрана, отправка push продолжится.
- Относится к: [D-041](#d-041)

## Приложение. Как получен отчёт

**Метод.**

1. Документ читается и делится на блоки (абзацы, пункты, строки таблиц); номера строк берутся из исходного текста. Значения, похожие на номера карт и ИИН, маскируются до любой обработки.
2. Блоки делятся на требования и служебные части моделью; программа проверяет, что каждый блок попал ровно в одно место, и сама присваивает номера REQ-….
3. Автоматические правила (набор 1.0) ищут формальные дефекты: размытые слова, заглушки, единицы измерения, коды и методы HTTP, пустые разделы, подсадной текст для ИИ.
4. Модель проверяет каждое требование по семи критериям ISO/IEC/IEEE 29148:2018 п. 5.2.5 тремя отдельными проходами (ясность; полнота и проверяемость; корректность) и весь набор по пяти критериям п. 5.2.6; затем второй, независимый проход перепроверяет каждое замечание.
5. Каждую цитату программа ищет в тексте документа; замечание без найденной цитаты выбрасывается, в отчёт попадает исходный текст, а не пересказ. Номера, индексы и вердикт считает программа.

**Честно о границах.** Это первый проход, который экономит время проверяющего; решение остаётся за человеком. Опубликованные замеры ИИ-проверки требований показывают, что лучшие модели находят примерно половину настоящих проблем и ошибочно помечают около одного требования из десяти. Поэтому цитаты сверяет программа, замечания модели перепроверяются вторым проходом, а полнота агента измеряется на контрольных документах, которых он раньше не видел.

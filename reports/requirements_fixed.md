### Общие сведения

### Цели
Дать клиенту возможность узнать о достижении личного бюджета в момент покупки.

### Архитектура решения
Мобильное приложение → сервис настроек. Карточный процессинг → учёт расходов → сервис push.

### Дизайн процесса UI
Карты → Расходы → Уведомления. На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить». При ошибке ввода сообщение появляется под полем.

### Требования к изменениям

#### BPMN схема процесса
Процессинг → сервис расходов: проведена покупка. Сервис расходов → настройки: получить порог карты. Сервис расходов → push: передать последние четыре цифры карты и сумму при достижении порога. Если сервис настроек или сервис push недоступен, сервис расходов повторяет обращение в течение 5 минут, затем записывает ошибку в журнал. Признак отправки ставится только после успешной передачи в сервис push.

#### Функциональные требования
* **Ф-1.** Держатель активной карты KZT задаёт целый порог от 1 000 до 1 000 000 ₸ включительно. По умолчанию уведомление выключено.
* **Ф-2.** Месяц определяется по дате совершения покупки в Алматы. В расходы входят проведённые покупки. Возврат уменьшает расходы месяца исходной покупки. Переводы и снятие наличных исключаются.
* **Ф-3.** Когда расходы переходят от суммы ниже порога к сумме, равной порогу или выше, клиент получает push. На карту приходится максимум один такой push за календарный месяц.
* **Ф-4.** При изменении порога накопленная сумма сохраняется. Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.

### Sequence Diagram
Процессинг → сервис расходов: проведена покупка. Сервис расходов → настройки: получить порог карты. Сервис расходов → push: при достижении порога передать последние четыре цифры карты и накопленные расходы месяца в тиынах. Если сервис настроек или сервис push недоступен, сервис расходов повторяет обращение в течение 5 минут, затем записывает ошибку в журнал. Признак отправки ставится только после успешной передачи в сервис push.

### Нефункциональные требования
Когда сервис расходов получает от карточного процессинга событие о проведённой покупке, которое приводит к достижению порога, сервис должен передать push на отправку не позднее чем через 1 минуту после получения этого события.

### Требования к данным
Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог в тенге.

### Требования к интеграции
Приложение читает порог, переключатель и сумму расходов за месяц новым методом GET, а сохраняет настройки методом сохранения порога; оба метода описываются в дочернем документе «Уведомление о расходах по карте — REST API». Событие процессинга с уже обработанным идентификатором операции считается повтором: оно не меняет сумму расходов и не вызывает второй push.

## Часть B. REST API

Дочерний документ части A: «Уведомление о расходах по карте — REST API».

### Общие параметры

| Поле | Значение |
| :--- | :--- |
| **Description** | Сохранение порога. Функциональные требования: чтение порога |
| **REST type** | GET |
| **Authorization** | Bearer, сессия владельца карты |
| **Controller** | AlertsController |
| **URL type** | Dev / Prod |
| **Request URL** | Dev: `/alerts/saveLimit` . Prod: — |
| **CURL** | `curl -G "$BASE/alerts/saveLimit" -H "Authorization: Bearer $TOKEN" --data 'cardId=demo-42&amount=50000&enabled=1'` |
| **Swagger** | — |
| **Gitlab project** | Учебный контур |
| **Framework** | Учебный контур |
| **Author** | Школа тестирования |
| **Developer** | Команда практикума |

### Логика работы метода
1. Проверить пользовательскую сессию.
2. Проверить принадлежность карты клиенту.
3. Проверить сумму и переключатель.
4. Когда проверки пройдены, сервис должен заменить действующий порог и признак включения карты на переданные и вернуть код 200 с полями result=OK, amount и enabled.
5. При отклонении суммы не менять сохранённую настройку и вернуть код 400 с телом, содержащим только result=ERROR и message.

### Особые правила
1. Пока порог сохраняется, сервис должен принимать amount только как целое число тенге от 1 000 до 1 000 000 включительно.
2. Повторное сохранение заменяет действующую настройку. Признак отправки push сбрасывается, только если изменилось значение порога; сохранение того же значения порога и изменение только переключателя признак не сбрасывают.
3. Изменение порога сохраняет накопленные расходы.

### Схема
```text
Приложение → AlertsController → хранилище настроек → AlertsController → приложение.
```

### Параметры запроса

### Ответ
Если результат 200 или 201 — успешный. Если результат 400, 401 и далее — неуспешный.

| Parameter | Format | Logic | Description | DB field |
| :--- | :--- | :--- | :--- | :--- |
| `result` | string | OK / ERROR | Исход сохранения | — |
| `amount` | string | При успехе | Порог в тенге | `limit_kzt` |
| `enabled` | string | «0» или «1» | Признак включения | `enabled` |
| `message` | string | При ошибке | Описание ошибки | — |

### Статусы

**200.** Ответ в случае успешного выполнения метода.  
**400.** Ответ в случае, если параметры запроса заполнены неверно.

#### 200. Successful — Created
```json
{"result":"OK","amount":"50000","enabled":"1"}
```
или
```json
{"result":"ERROR","message":"Проверьте сумму"}
```

**401.** Ответ в случае, если запрос выполнен без необходимой авторизации.  
**403.** Ответ в случае, если на указанный ресурс доступ запрещен.  
**500.** Ответ в случае, если произошла внутренняя ошибка сервера.

#### 400. Unsuccessful — Bad request
```json
{"message":"Некорректный запрос"}
```

#### 401. Unsuccessful — Unauthorized
```json
{"message":"Требуется вход"}
```

#### 403. Unsuccessful — Forbidden
Для чужой карты возвращается 404, как и для отсутствующей карты.  
**404**
```json
{"message":"Карта не найдена"}
```

#### 500. Unsuccessful — Internal server error
```json
{"message":"Ошибка сервиса"}
```
